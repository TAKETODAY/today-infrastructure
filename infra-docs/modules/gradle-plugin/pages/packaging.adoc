[[packaging-executable]]
= 打包可执行归档
include::partial$attributes.adoc[]
此插件可以创建包含应用所有依赖的可执行归档（jar 文件和 war 文件），并通过 `java -jar` 运行。



[[packaging-executable.jars]]
== 打包可执行 jar
可以使用 `infraJar` 任务构建可执行 jar。
应用 `java` 插件时，会自动创建此任务，其类型为 {infra-jar-javadoc}[`InfraJar`]。
`assemble` 任务会自动配置为依赖 `infraJar`，因此运行 `assemble`（或 `build`）时也会运行 `infraJar`。



[[packaging-executable.wars]]
== 打包可执行 war
可以使用 `infraWar` 任务构建可执行 war。
应用 `war` 插件时，会自动创建此任务，其类型为 {infra-war-javadoc}[`InfraWar`]。
`assemble` 任务会自动配置为依赖 `infraWar`，因此运行 `assemble`（或 `build`）时也会运行 `infraWar`。

NOTE: 应优先使用 `providedRuntime`，而不是 Gradle 的 `compileOnly` 配置。除了其他限制外，`compileOnly` 依赖不会出现在测试类路径中，因此依赖这些容器类的 Web 集成测试会失败。

[[packaging-executable.configuring]]

因此，打包普通 jar 或 war 时可用的所有标准配置选项，也同样适用于可执行 jar 或 war。
此外，还提供了一些专用于可执行 jar 和 war 的配置选项。

[[packaging-executable.configuring.launch-script]]
=== 创建可直接执行的归档
Infra 支持可直接执行的归档（fully executable archive）。
通过在归档前添加用于启动应用的 shell 脚本，即可使归档具备直接执行的能力。

[[packaging-executable.configuring.layered-archives]]
=== 打包分层 jar 或 war
默认情况下，`infraJar` 任务构建的归档将应用类和依赖分别放在 `APP-INF/classes` 和 `APP-INF/lib` 中。
类似地，`infraWar` 构建的归档将应用类放在 `WEB-INF/classes` 中，将依赖放在 `WEB-INF/lib` 和 `WEB-INF/lib-provided` 中。
如果需要根据 jar 的内容构建 Docker 镜像，进一步划分这些目录的内容，使其能够写入不同的镜像层，会很有帮助。

分层 jar 与 Infra 打包的普通可执行 jar 使用相同的布局，但额外包含一个描述各层的元数据文件。

默认定义了以下层：

* `dependencies`：版本中不包含 `SNAPSHOT` 的所有非项目依赖。
* `infra-app-loader`：jar 加载器类。
* `snapshot-dependencies`：版本中包含 `SNAPSHOT` 的所有非项目依赖。
* `application`：项目依赖、应用类和资源。

层的顺序非常重要，因为它决定了应用的部分内容发生变化时，前面的层有多大可能被缓存复用。
默认顺序为 `dependencies`、`infra-app-loader`、`snapshot-dependencies`、`application`。
应先添加最不容易变化的内容，再添加更容易变化的层。

可以按如下方式禁用此功能：

----

==== 自定义分层配置
根据应用的需要，你可能希望调整层的创建方式，或添加新的层。

为此，可以配置 jar 或 war 的分层规则以及各层的顺序。

.Groovy
----

----

`layered` DSL 由三个部分组成：

* `application` 闭包定义应用类和资源的分层方式。
* `dependencies` 闭包定义依赖的分层方式。
* `layerOrder` 方法定义各层的写入顺序。

在 `application` 和 `dependencies` 中，通过嵌套的 `intoLayer` 闭包将内容归入指定层。
这些闭包按照定义顺序从上到下求值。
尚未被前面的 `intoLayer` 闭包归入某一层的内容，仍可由后续闭包处理。

`intoLayer` 闭包通过嵌套的 `include` 和 `exclude` 调用选择内容。
`application` 闭包的包含和排除参数使用 Ant 风格的路径匹配。
`dependencies` 部分使用 `group:artifact[:version]` 模式。
它还提供了 `includeProjectDependencies()` 和 `excludeProjectDependencies()` 方法，用于包含或排除项目依赖。

如果没有调用 `include`，则会考虑所有尚未被前面的闭包分配的内容。

如果没有调用 `exclude`，则不排除任何内容。

在上例的 `dependencies` 闭包中，第一个 `intoLayer` 会将所有项目依赖归入 `application` 层。
下一个 `intoLayer` 会将剩余的所有 SNAPSHOT 依赖归入 `snapshot-dependencies` 层。
第三个也是最后一个 `intoLayer` 会将剩余的所有依赖（此处即既不是项目依赖也不是 SNAPSHOT 的依赖）归入 `dependencies` 层。

`application` 闭包也采用类似规则。
首先将 `infra/app/loader/**` 匹配的内容归入 `infra-app-loader` 层。
然后将剩余的所有类和资源归入 `application` 层。

NOTE: `intoLayer` 闭包的添加顺序通常不同于各层的写入顺序。
因此，必须始终调用 `layerOrder` 方法，并且其参数_必须_涵盖 `intoLayer` 调用中引用的所有层。
