[[mvc-ann-requestmapping]]
= 请求映射

本节讨论了注解控制器的请求映射。

[[mvc-ann-requestmapping-annotation]]
== `@RequestMapping`

使用 `@RequestMapping` 将请求映射到控制器方法。映射可以按 URL 路径、HTTP 方法、请求参数、请求头、媒体类型和 API 版本匹配。
可以在类级别声明共享条件，再在方法级别声明具体端点。`value` 和 `path` 互为别名，都可以指定一个或多个路径模式。

以下 xref:web/webmvc/mvc-controller/ann-requestmapping.adoc#mvc-ann-requestmapping-composed[组合注解] 是指定 HTTP 方法的快捷方式：

* `@GET` 或 `@GetMapping`
* `@POST` 或 `@PostMapping`
* `@PUT` 或 `@PutMapping`
* `@DELETE` 或 `@DeleteMapping`
* `@PATCH` 或 `@PatchMapping`
* `@QUERY` 或 `@QueryMapping`

建议为控制器端点显式指定 HTTP 方法。不设置 `method` 时，该条件通常不限制 HTTP 方法；
普通 OPTIONS 请求由框架 xref:web/webmvc/mvc-controller/ann-requestmapping.adoc#mvc-ann-requestmapping-head-options[默认处理]。

NOTE: `@RequestMapping` 不能与在同一元素（类、接口或方法）上声明的其他 `@RequestMapping`
注解一起使用。如果在同一个元素上检测到多个 `@RequestMapping` 注解，将记录一条警告，并且只使用第一个映射。
这也适用于诸如 `@GET`、`@POST` 等组合的 `@RequestMapping` 注解。

以下示例具有类型和方法级别的映射：

[source,java,indent=0,subs="verbatim,quotes",role="primary"]
----
@RestController
@RequestMapping("/persons")
class PersonController {

  @GET("/{id}")
  public Person getPerson(@PathVariable Long id) {
    // ...
  }

  @POST
  @ResponseStatus(HttpStatus.CREATED)
  public void add(@RequestBody Person person) {
    // ...
  }
}
----

[[mvc-ann-requestmapping-combine]]
=== 类级别与方法级别映射的合并

方法级别的 `combine` 默认为 `true`。类级别和方法级别的路径会合并；如果两级都声明了 HTTP 方法，取并集而不是交集。
如果两级都设置了 `name`，映射名称会以 `#` 拼接，例如 `persons#get`。

在方法级别设置 `combine = false` 可以跳过整个类级别映射，而不只是跳过类级别的路径。
例如，在上面的 `PersonController` 中，`@GET(path = "/people", combine = false)` 映射的是 `/people`，而不是 `/persons/people`。
此选项不会跳过通过 xref:web/webmvc/mvc-config/path-matching.adoc[MVC 路径匹配配置] 添加的全局路径前缀。


[[mvc-ann-requestmapping-uri-templates]]
== URI 匹配

Web MVC 使用预先解析的 `PathPattern` 匹配请求路径。请求路径表示为 `PathContainer`，可以逐段处理 URL 编码和路径参数。
有关匹配选项，请参阅 xref:web/webmvc/mvc-config/path-matching.adoc[MVC 配置]。

`+**+` 和 `+{*name}+` 都匹配零个或多个路径段，后者还会将匹配到的路径捕获为变量。
每个模式只能包含一个这样的多段匹配元素，且只能放在模式开头或末尾。
完整语法参见 {today-framework-api}/web/util/pattern/PathPattern.html[`PathPattern`]。

路径模式示例：

* `+"/resources/ima?e.png"+` -- 在路径段中匹配一个字符
* `+"/resources/*.png"+` -- 在路径段中匹配零个或多个字符
* `+"/resources/**"+` -- 匹配 `/resources` 后的零个或多个路径段
* `+"/{*path}/info"+` -- 将 `/info` 前的路径捕获为 `path`，例如从 `/docs/api/info` 捕获 `/docs/api`
* `+"/projects/{project}/versions"+` -- 匹配一个路径段并将其捕获为变量
* `+"/projects/{project:[a-z]+}/versions"+` -- 匹配并捕获具有正则表达式的变量

捕获的 URI 变量可以使用 `@PathVariable` 访问。例如：

[source,java,indent=0,subs="verbatim,quotes",role="primary"]
----
@GET("/owners/{ownerId}/pets/{petId}")
public Pet findPet(@PathVariable Long ownerId, @PathVariable Long petId) {
  // ...
}
----

你可以在类或者方法上声明 URI 变量，例如：

[source,java,indent=0,subs="verbatim,quotes",role="primary"]
----
@Controller
@RequestMapping("/owners/{ownerId}")
public class OwnerController {

  @GET("/pets/{petId}")
  public Pet findPet(@PathVariable Long ownerId, @PathVariable Long petId) {
    // ...
  }

}
----

URI 变量会自动转换为适当的类型，或者抛出 `TypeMismatchException`。
简单类型（如 `int`、`long`、`Date` 等）默认受到支持，您可以注册对任何其他数据类型的支持。
请参阅 xref:web/webmvc/mvc-controller/ann-methods/typeconversion.adoc[类型转换]
和 xref:web/webmvc/mvc-controller/ann-initbinder.adoc[`DataBinder`]。

您可以显式命名 URI 变量（例如，`@PathVariable("customId")`），但如果名称相同，并且您的代码使用了
`-parameters` 编译器标志进行编译，则可以省略此细节。

语法 `+{varName:regex}+` 为 URI 变量添加正则表达式约束。
例如，给定 URL `/infra-web-4.0.0.jar`，以下方法提取名称、版本和文件扩展名：

[source,java,indent=0,subs="verbatim,quotes",role="primary"]
----
@GET("/{name:[a-z-]+}-{version:\\d\\.\\d\\.\\d}{ext:\\.[a-z]+}")
public void handle(@PathVariable String name, @PathVariable String version, @PathVariable String ext) {
  // ...
}
----

路径模式也可以包含 `+${...}+` 占位符，例如 `+${api.base-path}/pets+`。
框架在注册映射时解析占位符，因此可以通过外部配置指定端点的路径前缀。


[[mvc-ann-requestmapping-pattern-comparison]]
== 路径模式的优先级

如果多个映射都匹配同一个请求，框架会使用
{today-framework-api}/web/util/pattern/PathPattern.html#SPECIFICITY_COMPARATOR[`PathPattern.SPECIFICITY_COMPARATOR`]
比较路径模式的具体程度：

* 含 `+**+` 或 `+{*name}+` 的模式排在其他模式之后；如果两者都含多段匹配元素，优先选择规范化后更长的模式。
* 按得分从低到高排序。捕获变量的权重低于 `+*+` 通配符，例如 `+/pets/{id}+` 比 `+/pets/*+` 更具体。
* 得分相同时，优先选择规范化后更长的模式。例如，单独占据一个路径段的捕获变量按一个字符计。

如果路径模式无法区分候选映射，框架还会比较请求参数、请求头、媒体类型等映射条件。


[[mvc-ann-requestmapping-consumes]]
== 可处理的媒体类型

您可以根据请求的 `Content-Type` 来缩小请求映射的范围，如下例所示：

[source,java,indent=0,subs="verbatim,quotes",role="primary"]
----
@POST(path = "/pets", consumes = "application/json") // <1>
public void addPet(@RequestBody Pet pet) {
  // ...
}
----
<1> 使用 `consumes` 属性通过内容类型来缩小映射范围。

`consumes` 属性还支持否定表达式--例如，`!text/plain` 表示除了 `text/plain` 之外的任何内容类型。

您可以在类级别声明共享的 `consumes` 属性。然而，与大多数其他请求映射属性不同，当在类级别使用时，
方法级别的 `consumes` 属性会覆盖而不是扩展类级别的声明。

TIP: `MediaType` 提供了常用媒体类型的常量，如 `APPLICATION_JSON_VALUE` 和 `APPLICATION_XML_VALUE`。


[[mvc-ann-requestmapping-produces]]
== 返回的媒体类型

您可以根据 `Accept` 请求头和控制器方法产生的内容类型列表来缩小请求映射的范围，如下例所示：

[source,java,indent=0,subs="verbatim,quotes",role="primary"]
----
@GET(path = "/pets/{petId}", produces = "application/json") // <1>
@ResponseBody
public Pet getPet(@PathVariable String petId) {
  // ...
}
----
<1> 使用 `produces` 属性通过内容类型来缩小映射范围。

媒体类型可以指定字符集。支持否定表达式——例如，`!text/plain` 表示除了 "text/plain" 之外的任何内容类型。

您可以在类级别声明共享的 `produces` 属性。然而，与大多数其他请求映射属性不同，当在类级别使用时，
方法级别的 `produces` 属性会覆盖而不是扩展类级别的声明。

TIP: `MediaType` 提供了常用媒体类型的常量，如 `APPLICATION_JSON_VALUE` 和 `APPLICATION_XML_VALUE`。


[[mvc-ann-requestmapping-params-and-headers]]
== 请求参数和请求头

可以根据请求参数条件缩小映射范围。支持检查参数是否存在（`myParam`）、是否不存在（`!myParam`）、
是否等于指定值（`myParam=myValue`）或是否不等于指定值（`myParam!=myValue`）。声明多个条件时，必须同时满足。
以下示例检查参数值：

[source,java,indent=0,subs="verbatim,quotes",role="primary"]
----
@GET(path = "/pets/{petId}", params = "myParam=myValue") // <1>
public void findPet(@PathVariable String petId) {
  // ...
}
----
<1> 检查 `myParam` 是否等于 `myValue`。

您也可以使用相同的方法来测试请求头条件，如下例所示：

[source,java,indent=0,subs="verbatim,quotes",role="primary"]
----
@GET(path = "/pets/{petId}", headers = "myHeader=myValue") // <1>
public void findPet(@PathVariable String petId) {
  // ...
}
----
<1> 检查 `myHeader` 是否等于 `myValue`。

TIP: 您可以使用头条件匹配 `Content-Type` 和 `Accept`，但最好使用 xref:web/webmvc/mvc-controller/ann-requestmapping.adoc#mvc-ann-requestmapping-consumes[consumes]
和 xref:web/webmvc/mvc-controller/ann-requestmapping.adoc#mvc-ann-requestmapping-produces[produces] 代替。


[[mvc-ann-requestmapping-version]]
== API 版本

配置 xref:web/webmvc-versioning.adoc#mvc-versioning-mapping[API 版本管理] 后，可以用 `version` 属性区分同一端点的不同版本，
例如 `@GET(path = "/pets", version = "1.2")`。`"1.2"` 是固定版本，要求精确匹配；`"1.2+"` 是基线版本，
可以匹配 `1.2` 及更高的受支持版本。其他映射条件相同时，框架优先选择不高于请求版本的最高声明版本，再校验固定版本是否精确匹配。

方法级别声明的 `version` 会覆盖类级别版本；未声明时，默认沿用类级别版本。


[[mvc-ann-requestmapping-query]]
== HTTP QUERY

`@QUERY` 和 `@QueryMapping` 都等价于 `@RequestMapping(method = HttpMethod.QUERY)`。
HTTP QUERY 是一种可以携带请求体的只读查询方法（参见 https://www.rfc-editor.org/rfc/rfc10008.html[RFC 10008]）。
例如，可以用 `@QUERY(path = "/pets/search", consumes = "application/json")` 映射接收 JSON 查询条件的端点，
并用 `@RequestBody` 读取查询条件。


[[mvc-ann-requestmapping-head-options]]
== HTTP HEAD 和 OPTIONS

`@GET`、`@GetMapping` 和 `@RequestMapping(method = HttpMethod.GET)` 也匹配 HEAD 请求。
框架不会发送响应体。显式声明的 HEAD 映射优先于 GET 映射提供的隐式 HEAD 支持。

没有显式映射处理普通 OPTIONS 请求时，框架从路径匹配的映射中收集已声明的 HTTP 方法，并通过 `Allow` 响应头返回。
`Allow` 会包含 `OPTIONS`；存在 GET 或 QUERY 映射时，也会包含 `HEAD`。
如果没有收集到显式声明的 HTTP 方法，`Allow` 包含 `HttpMethod` 定义的除 `TRACE` 以外的所有方法。

默认的 OPTIONS 响应通过 `Accept-Patch` 和 `Accept-Query` 公告 PATCH 和 QUERY 请求体可用的媒体类型（如已声明）。
如果 HEAD 请求没有匹配的 HTTP 方法条件，但该路径声明了 QUERY 映射，框架也会通过 `Accept-Query` 公告媒体类型，
而不会调用 QUERY 控制器方法。



[[mvc-ann-requestmapping-composed]]
== 自定义注解

Web MVC 支持使用 xref:core/beans/classpath-scanning.adoc#beans-meta-annotations[组合注解]
进行请求映射。这些注解本身使用 `@RequestMapping` 进行元注解，并组合起来重新声明 `@RequestMapping`
的子集（或全部）属性，以实现更狭窄、更具体的目的。

`@GET`、`@POST` 和 `@QUERY` 都是组合注解。如果需要实现自己的组合注解，可以参考它们如何使用 `@AliasFor`
将属性映射到 `@RequestMapping`。

Web MVC 还支持使用自定义请求映射属性和自定义请求匹配逻辑。这是一个更高级的选项，需要通过扩展
`RequestMappingHandlerMapping` 并覆盖 `getCustomCondition` 方法来实现，
在那里您可以检查自定义属性并返回您自己的 `RequestCondition`。


[[mvc-ann-requestmapping-registration]]
== 显式注册

可以以编程方式注册处理器方法，这可以用于动态注册或高级用例，例如在不同 URL 下使用相同的处理器的不同实例。
以下示例展示了如何注册一个处理器方法：

[source,java,indent=0,subs="verbatim,quotes",role="primary"]
----
@Configuration
public class MyConfig {

  @Autowired
  public void setHandlerMapping(RequestMappingHandlerMapping mapping, UserHandler handler) // <1>
      throws NoSuchMethodException {

    RequestMappingInfo info = RequestMappingInfo
        .paths("/user/{id}").methods(HttpMethod.GET)
        .options(mapping.getBuilderConfiguration()).build(); // <2>

    Method method = UserHandler.class.getMethod("getUser", Long.class); // <3>

    mapping.registerMapping(info, handler, method); // <4>
  }
}
----
<1> 注入目标处理器和控制器的处理器映射。
<2> 使用 `infra.http.HttpMethod` 准备请求映射元数据，并沿用处理器映射的构建配置。
<3> 获取处理器方法。
<4> 添加注册。

如需移除动态注册的映射，可以调用 `mapping.unregisterMapping(info)`。


[[mvc-ann-httpexchange-annotation]]
== `@HttpExchange`

虽然 `@HttpExchange` 的主要目的是通过生成的代理抽象 HTTP 客户端代码，但这样的注解所放置的
xref:integration/rest-clients.adoc#rest-http-interface[HTTP 接口] 是一个与客户端与服务器使用无关的契约。
除了简化客户端代码外，还有一些情况下，HTTP 接口可能是服务器方便地暴露其 API 供客户端访问的方式。
这导致客户端和服务器之间的耦合增加，通常不是一个好的选择，特别是对于公共 API，但可能正是内部 API 的目标。
这种方法也是为什么 `@HttpExchange` 被支持作为 `@RequestMapping` 的替代品，用于控制器类中的服务器端处理。

例如：

[source,java,indent=0,subs="verbatim,quotes",role="primary"]
----
@HttpExchange("/persons")
interface PersonService {

  @GetExchange("/{id}")
  Person getPerson(@PathVariable Long id);

  @PostExchange
  void add(@RequestBody Person person);
}

@RestController
class PersonController implements PersonService {

  public Person getPerson(@PathVariable Long id) {
    // ...
  }

  @ResponseStatus(HttpStatus.CREATED)
  public void add(@RequestBody Person person) {
    // ...
  }
}
----

`@HttpExchange` 和 `@RequestMapping` 在功能上有所区别：

* `@RequestMapping` 可以通过路径模式、HTTP 方法等条件匹配多种请求。
* `@HttpExchange` 声明的是客户端与服务器共享的单一端点契约。

NOTE: 同一个类、接口或方法不能同时声明 `@RequestMapping` 和 `@HttpExchange`（包括各自的组合注解）；框架会拒绝注册此类映射。

对于方法参数和返回值：

* 通常，`@HttpExchange` 支持 `@RequestMapping` 支持的方法参数的一个子集。
* 特别地，它不包括任何特定于服务器端的参数类型。

有关详细信息，请参阅：

* xref:integration/rest-clients.adoc#rest-http-interface-method-parameters[@HttpExchange] 方法参数的列表。
* xref:web/webmvc/mvc-controller/ann-methods/arguments.adoc[@RequestMapping] 方法参数的列表。
