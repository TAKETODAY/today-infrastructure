[[mvc-filters]]
= 过滤器

`infra.web.Filter` 用于在请求进入处理器之前执行检查，或围绕后续处理执行逻辑。
调用 `FilterChain.doFilter(HttpContext)` 将请求交给后续过滤器和处理器；
不调用过滤链并直接返回，则短路后续处理。

过滤器从 5.0 开始提供，运行在 `DispatcherHandler` 层，在处理器查找和执行之前介入。
它适合认证检查、限流、维护模式、请求日志和通用请求头处理等不依赖具体控制器的逻辑。
这里的 `Filter` 是框架的 `infra.web.Filter`，不是 Servlet 的过滤器接口。

== 注册与排序

将 `Filter` 注册为应用上下文中的 Bean 即可。`DispatcherHandler` 初始化时会自动发现当前上下文
及祖先上下文中的过滤器，并根据 `infra.core.annotation.Order` 或 `infra.core.Ordered` 排序。
数值越小的过滤器越先进入；有顺序要求时应显式指定不同的顺序值，不要依赖相同顺序值之间的排列。

可以像下文的认证过滤器一样使用 `@Component`，也可以通过 `@Bean` 注册。
`Filter` 是函数式接口，因此简单逻辑可以使用 Lambda 表达式：

[source,java]
----
import infra.context.annotation.Bean;
import infra.context.annotation.Configuration;
import infra.core.annotation.Order;
import infra.web.Filter;

@Configuration
public class FilterConfiguration {

  @Bean
  @Order(0)
  Filter responseHeaderFilter() {
    return (http, chain) -> {
      http.setHeader("X-Application", "example");
      chain.doFilter(http);
    };
  }
}
----

过滤器默认参与该调度器接收的所有请求，不需要通过 MVC 拦截器注册器注册。
需要按路径生效时，在过滤器中检查 `http.getRequestURI()` 等请求信息，
对不适用的请求直接调用过滤链并返回。
过滤器 Bean 通常由多个请求共享，不要将当前请求、响应或计时状态保存在实例字段中；
请求相关状态应保存在局部变量或 `HttpContext` 属性中。

== 执行顺序与前后置处理

过滤器通过 `doFilter(HttpContext, FilterChain)` 处理请求。通常只调用一次
`chain.doFilter(http)`；重复调用会再次执行下游链，而不是从上次结束的位置继续。
链的终点进入处理器查找、执行及返回值处理。
调用 `HttpContext.forward(path)` 则直接重新查找目标处理器，不会重新执行过滤器链。
参见 xref:web/webmvc/mvc-core/sequence.adoc#mvc-internal-forward[内部转发]。

例如，两个过滤器的顺序值分别为 `0` 和 `10`，正常同步执行时顺序如下：

[source,text]
----
Filter(0) 前置逻辑
  Filter(10) 前置逻辑
    处理器查找、执行及返回值处理
  Filter(10) 后置逻辑
Filter(0) 后置逻辑
----

如果前面的过滤器短路，后续过滤器和处理器不会执行。
使用 `try/finally` 可以在下游调用返回或抛出异常时释放过滤器自己持有的资源：

[source,java]
----
@Override
public void doFilter(HttpContext http, FilterChain chain) throws Exception {
  long start = System.nanoTime();
  try {
    chain.doFilter(http);
  }
  finally {
    long elapsedNanos = System.nanoTime() - start;
    // 将本次过滤链调用耗时写入指标或日志。
  }
}
----

这里的后置逻辑只表示过滤链调用已返回，不保证客户端已收到响应，
也不代表异步请求已经完成。需要跟随请求完成时机执行的动作，应使用
`HttpContext.registerCompletedCallback(Runnable)` 等生命周期回调，
而不是依赖过滤器的 `finally`。
同步处理返回时，响应可能已经提交、请求也可能已经完成，
因此应在调用过滤链之前设置响应头，不要把后置逻辑当作修改响应结果的入口。

注册生命周期回调时，如果不指定名称，每次注册都独立生效。例如，将同一个 `Runnable` 注册两次作为完成回调，请求完成时它会执行两次。
要取消其中一次注册，请在该阶段开始触发回调之前调用 `removeCallback(phase, name)`，传入注册时的阶段和该次注册返回的名称。
如果希望后注册的回调替换先前的回调，请使用 `registerCallback(phase, name, callback)`，在同一阶段显式指定相同名称。

== 与 HandlerInterceptor 的区别

[cols="1,2,2",options="header"]
|===
|比较项 |Filter |HandlerInterceptor
|介入位置 |处理器查找之前 |处理器已经匹配之后
|处理依据 |请求上下文，不要求存在匹配的处理器 |已解析的处理器及其处理流程
|典型用途 |全局认证、限流、请求日志、提前拒绝请求 |依赖具体处理器的检查和处理逻辑
|注册方式 |作为 `Filter` Bean 自动发现 |通过 MVC 拦截器配置等机制注册
|===

需要在没有匹配处理器时也执行的检查，应优先使用 `Filter`。
需要根据控制器方法或其注解执行的逻辑，更适合使用
xref:web/webmvc/mvc-core/handlermapping-interceptor.adoc[处理器拦截器]。

== 在过滤器中发送响应

从 5.0 开始，可以通过 `HttpContext.send(Object)` 发送响应结果，无需注入额外的发送器，
也不需要先匹配控制器方法。该方法复用已配置的返回值处理器和消息转换器。

下面的过滤器在缺少认证信息时发送 JSON 错误响应，否则继续过滤链。
示例仅演示短路响应，实际应用仍需验证凭据的有效性。

[source,java]
----
import java.util.Map;

import infra.http.HttpStatus;
import infra.http.MediaType;
import infra.http.ResponseEntity;
import infra.stereotype.Component;
import infra.web.Filter;
import infra.web.FilterChain;
import infra.web.HttpContext;

@Component
public class AuthenticationFilter implements Filter {

  @Override
  public void doFilter(HttpContext http, FilterChain chain) throws Exception {
    if (http.getHeader("Authorization") == null) {
      http.send(ResponseEntity.status(HttpStatus.UNAUTHORIZED)
          .contentType(MediaType.APPLICATION_JSON)
          .body(Map.of("code", "UNAUTHORIZED", "message", "请先登录")));
      return;
    }

    chain.doFilter(http);
  }
}
----

JSON 响应需要配置能够写入该对象类型的 JSON 消息转换器。
`ResponseEntity` 同时表达状态码、响应头和响应体；仅需发送对象时，也可以直接调用
`http.send(result)`，具体行为由配置的返回值处理器决定。

== 结果处理规则

`send` 将结果原样传给返回值处理器，不会自动包装为 `HttpEntity`，
也不会强制将所有结果解释为响应体。处理器选择时没有控制器方法元数据，
因此不能依赖控制器方法上的 `@ResponseBody` 等注解来决定处理方式。

* 字符串沿用现有的视图名处理规则，不会自动作为纯文本响应体。
* 发送文本响应体时，显式使用 `HttpEntity` 或 `ResponseEntity`。
* `null` 保持响应不变，不推断默认视图，也不自动设置为 `204 No Content`。
* 自定义返回值处理器接收到的仍是原始结果对象。

例如，发送纯文本响应体：

[source,java]
----
http.send(ResponseEntity.ok()
    .contentType(MediaType.TEXT_PLAIN)
    .body("Service is available"));
----

== 过滤链、异常与生命周期

`send` 只处理响应结果，不会调用过滤链，也不会主动完成请求生命周期。
过滤器发送短路响应后应立即 `return`，不要再调用 `chain.doFilter(http)`，
以免下游继续生成响应。请求完成和资源清理由外层调度流程负责。
方法返回不代表客户端已经收到全部响应。

响应已提交或请求已完成时，调用 `send` 会抛出 `IllegalStateException`，包括发送 `null` 的情况。
不要在下游已写入或完成响应后再次调用 `send` 来替换结果。

处理器选择、消息转换或响应写入失败时，异常会向调用方传播。
在正常的 `DispatcherHandler` 过滤链调用中，若请求尚未完成、未开始并发处理且响应尚未提交，
异常会进入调度器现有的异常处理流程；响应提交后不能依靠异常处理器重新生成响应。
