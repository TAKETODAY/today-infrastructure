[[features.external-config]]
= 外部化配置

TODAY INFRA 允许把配置放在应用代码之外，使同一份代码在不同环境中运行。
配置来源包括 Java Properties、YAML、环境变量、Java 系统属性和命令行参数。
可以通过 `infra.beans.factory.annotation.Value` 注入单个值，通过 `infra.core.env.Environment` 查询属性，或使用 `infra.context.properties.ConfigurationProperties` 绑定结构化对象。

== 配置文件搜索路径

应用启动时，默认查找 `application.properties` 和支持的 YAML 变体。
默认位置按以下顺序处理，后面的配置可以覆盖前面的配置：

. 类路径根目录。
. 类路径的 `/config/` 包。
. 当前工作目录。
. 当前工作目录的 `config/` 子目录。
. `config/` 的直接子目录。

推荐在整个应用中使用同一种格式。同一位置同时存在 Properties 和 YAML 时，Properties 的优先级更高。
类路径中的配置适合提供默认值，外部配置适合部署时覆盖默认值。
命令行属性优先于配置文件；Java 系统属性优先于操作系统环境变量，二者优先于默认加载的配置文件。
通过 `Application.setDefaultProperties(...)` 提供的默认属性位于较低优先级。
测试框架、自定义环境或属性源后处理器可以进一步调整属性源，不应把这些常见来源的顺序当成所有环境的完整列表。

`@PropertySource` 的属性源直到上下文刷新时才加入，因此不能用它设置在刷新前就读取的启动和日志选项。

== 命令行参数

`Application` 默认把 `--` 开头的选项转换为环境属性，例如 `--server.port=9000`。
如果不希望这样处理，启动前调用 `setAddCommandLineProperties(false)`。

[source,shell]
----
java -jar myapp.jar --my.service.name=production
----

== JSON 属性

可以用 `infra.application.json` 系统属性或 `INFRA_APPLICATION_JSON` 环境变量提供一段 JSON：

[source,shell]
----
INFRA_APPLICATION_JSON='{"my":{"name":"test"}}' java -jar myapp.jar
java -Dinfra.application.json='{"my":{"name":"test"}}' -jar myapp.jar
java -jar myapp.jar --infra.application.json='{"my":{"name":"test"}}'
----

解析后，环境中会出现 `my.name=test`。
该 JSON 属性源位于系统属性之前；通常仍低于命令行属性。
目标实现把 JSON 的 `null`、空对象和空数组转换为空字符串。这与上游页面中“`null` 不能覆盖较低优先级属性”的说明不同，不应照搬该说明。

== 更改名称和位置

`app.config.name` 更改配置文件基本名称，不包含扩展名：

[source,shell]
----
java -jar myapp.jar --app.config.name=myproject
----

`app.config.location` 替换默认搜索位置；`app.config.additional-location` 增加位置，新增位置可以覆盖默认位置的值。
多个位置以逗号分隔，目录位置应以 `/` 结尾。
位置按声明顺序处理，后面的位置可以覆盖前面的值；分号 `;` 把位置归为同一优先级组。

[source,shell]
----
java -jar myapp.jar --app.config.additional-location=optional:file:./custom-config/
----

这些属性在加载配置文件之前就会读取，必须通过命令行、系统属性或环境变量等早期来源设置。
不要把 `app.config.name` 放进希望由它决定文件名的配置文件中。

目录位置会追加由 `app.config.name` 生成的文件名；文件位置则直接加载指定文件。
两种位置都会考虑 Profile 专用变体，例如 `classpath:myconfig.properties` 也会查找适用的 `myconfig-prod.properties`。

例如，将 `app.config.location` 设置为 `optional:classpath:/custom-config/,optional:file:./custom-config/` 后，只搜索这两个自定义位置，不再搜索默认位置。
如果改用同样的 `app.config.additional-location`，则先搜索默认位置，再搜索两个自定义位置：

. `optional:classpath:/;optional:classpath:/config/`
. `optional:file:./;optional:file:./config/;optional:file:./config/*/`
. `optional:classpath:/custom-config/`
. `optional:file:./custom-config/`

这样可以在打包配置中提供默认值，再由部署环境中的文件选择性覆盖。

=== 可选位置

指定的位置不存在时，默认会抛出 `ConfigDataLocationNotFoundException`，阻止启动。
如果允许某个位置不存在，添加 `optional:` 前缀；该前缀可以用于 `location`、`additional-location` 和 `import`。
`app.config.on-not-found=ignore` 可忽略配置数据位置不存在的错误，应明确了解缺失配置的影响后再使用。

=== 通配符位置

外部目录支持最后一个路径段中的通配符，例如 `file:./config/*/`。
默认搜索位置已经包含当前目录下的 `config/*/`。
通配符仅用于外部位置，不能用于 `classpath:`；子目录按绝对路径的字母顺序处理。
需要不同优先级时，显式列出各个位置。

例如，分别挂载 `/config/redis/application.properties` 和 `/config/mysql/application.properties` 时，`config/*/` 可以同时发现这两份配置。
通配符位置只能包含一个 `*`；目录搜索必须以 `*/` 结尾，文件搜索必须采用 `*/<filename>` 形式。

=== Profile 专用文件

`application-prod.properties` 等 Profile 专用文件覆盖同位置的普通配置。
多个激活的 Profile 采用后者优先规则，例如 `prod,live` 中 `live` 的值可以覆盖 `prod`。
此规则作用于位置组：`classpath:/cfg/,classpath:/ext/` 先处理整个 `cfg` 再处理 `ext`，而 `classpath:/cfg/;classpath:/ext/` 把二者放在同一组内按 Profile 处理。
没有激活的 Profile 时，会考虑默认 Profile（默认是 `default`）对应的文件。
更多 Profile 设置见 xref:features/profiles.adoc[]。

==== 位置组与覆盖顺序

假设激活的 Profile 顺序为 `prod,live`，并存在以下文件：

[source,text]
----
/cfg
  application-live.properties
/ext
  application-live.properties
  application-prod.properties
----

使用 `app.config.location=classpath:/cfg/,classpath:/ext/` 时，逗号将两个目录划为不同组。
先处理 `/cfg` 组的全部 Profile，再处理 `/ext` 组：

. `/cfg/application-live.properties`
. `/ext/application-prod.properties`
. `/ext/application-live.properties`

使用 `app.config.location=classpath:/cfg/;classpath:/ext/` 时，两个目录属于同一组，按 Profile 顺序遍历组内位置：

. `/ext/application-prod.properties`
. `/cfg/application-live.properties`
. `/ext/application-live.properties`

因此，逗号与分号并非可以任意互换的分隔符。
在 shell 命令中使用分号时，应给整个参数加引号，避免被 shell 当作命令分隔符。
每个配置文件只加载一次；已直接导入的 Profile 专用文件不会再次重复导入。

== 导入配置数据

使用 `app.config.import` 从其他位置导入配置数据：

[source,properties]
----
app.config.import=optional:file:./dev.properties
----

导入文件的值优先于声明导入的文档。
同一位置只导入一次，单个文档中 `import` 属性的书写位置不会改变优先级。
多个导入按声明顺序处理，后面的导入优先；适用时也加载 Profile 专用变体。

以 `/` 或 `file:`、`classpath:` 等协议前缀开头的位置是固定位置。
其他位置相对于声明导入的文件解析，`optional:` 不影响这一判断。
例如 `/demo/application.properties` 中的 `optional:core/core.properties` 指向 `/demo/core/core.properties`。

=== 链式相对导入

假设应用位于 `/demo`，其 `/demo/application.properties` 包含：

[source,properties]
----
app.config.import=optional:core/core.properties
----

如果 `/demo/core/core.properties` 又包含：

[source,properties]
----
app.config.import=optional:extra/extra.properties
----

第二次导入指向 `/demo/core/extra/extra.properties`，而不是 `/demo/extra/extra.properties`。
每一级相对导入都以声明它的配置文件所在目录为基准，`optional:` 只控制缺失时是否允许继续启动。

=== 导入声明的顺序与扩展点

下列两个文档的效果相同：

[source,properties]
----
app.config.import=my.properties
my.property=value
----

[source,properties]
----
my.property=value
app.config.import=my.properties
----

两种写法中，`my.properties` 的属性都优先于声明导入的文档。
如果导入 `my.properties` 且存在适用的 `my-prod.properties` 等变体，也会考虑这些 Profile 专用文件。

默认支持的导入形式包括 Properties、YAML、环境变量内容与配置树。
第三方库可以通过 `infra.app.context.config.ConfigDataLocationResolver` 与 `ConfigDataLoader` 支持其他位置或外部存储，不要求配置一定来自本地文件。
扩展实现需要按目标项目的 `META-INF/infra.strategies` 机制注册，不能直接使用 Boot 的注册文件名。

=== 无扩展名文件

可以使用扩展名提示加载没有扩展名的文件：

[source,properties]
----
app.config.import=file:/etc/config/myconfig[.yaml]
----

`[.yaml]` 是 `[extension=.yaml]` 的简写。也可以指定文件编码，或组合两种提示：

[source,properties]
----
app.config.import=classpath:import.properties[encoding=utf-8]
app.config.import=file:/etc/config/myconfig[extension=.properties][encoding=utf-8]
----

编码提示会传递给配置加载器；Properties 加载器支持指定字符集，未指定时保持原有默认编码。

NOTE: 扩展名提示必须位于位置字符串的末尾。
其他位置的方括号视为路径的一部分。
例如，`file:/etc/config[prod]/myconfig[.yaml]` 会将 `/etc/config[prod]/myconfig` 作为 YAML 文件导入。

=== 从环境变量导入配置

`env:` 将一个环境变量的完整内容作为配置文档加载，而不是将环境变量名作为单个属性名。
默认按 Java Properties 格式解析：

[source,properties]
----
app.config.import=env:MY_CONFIGURATION
----

例如，`MY_CONFIGURATION` 可以包含多行 `server.port=8081`、`app.name=demo` 配置。
使用 YAML 时添加扩展名提示：

[source,properties]
----
app.config.import=env:MY_CONFIGURATION[.yaml]
----

支持 YAML 多文档。环境变量不存在时启动失败；使用 `optional:env:MY_CONFIGURATION` 可忽略缺失变量。
默认使用 JVM 默认字符集对环境变量内容进行编码，并将同一字符集传给配置加载器，避免 Properties 默认编码导致中文等字符乱码。
`env:` 位置也支持 `[extension=.properties][encoding=UTF-8]` 形式的提示；
普通文件导入同样支持前述扩展名与编码提示。
环境变量可能包含敏感配置，请不要将其内容输出到日志。

=== 配置树

配置树把目录和文件名组成属性名，把文件内容作为属性值，适合读取挂载到文件系统的配置或 Secret：

[source,properties]
----
app.config.import=optional:configtree:/etc/config/
----

如果目录下有 `myapp/username` 和 `myapp/password`，得到 `myapp.username` 和 `myapp.password`。
从 `/etc/config/myapp/` 导入则得到 `username` 和 `password`。
文件名中的点也作为属性名的一部分，值可以绑定为 `String` 或 `byte[]`。
`configtree:/etc/config/*/` 可以导入直接子目录中的配置树，目录按字母顺序处理。
Docker Secret 也可以通过 `optional:configtree:/run/secrets/` 导入。

挂载卷通常有两种布局：一个文件包含完整 YAML 或 Properties 文档，或者目录中的每个文件各自对应一个配置值。
前一种使用普通文件导入；后一种才使用 `configtree:`，二者不能混淆。
例如：

[source,text]
----
etc/
  config/
    dbconfig/
      db/
        username
        password
    mqconfig/
      mq/
        username
        password
----

使用下面的导入可以同时读取两个配置树：

[source,properties]
----
app.config.import=optional:configtree:/etc/config/*/
----

得到的属性名为 `db.username`、`db.password`、`mq.username` 和 `mq.password`，不包含通配符所匹配的 `dbconfig`、`mqconfig` 目录名。
每个匹配的直接子目录分别作为配置树根目录；它下面的目录和文件名才组成属性名。
如果需要不同于字母顺序的覆盖规则，应分别显式声明各个导入位置。
Docker Secret 文件名本身也可以包含点，例如 `/run/secrets/db.password` 会暴露为 `db.password`。

== 占位符与多文档配置

配置值使用时可通过环境解析 `$\{name}` 占位符，也可以指定默认值 `${name:default}`。
推荐使用小写连字符形式的规范属性名，例如 `${demo.item-price}`。

[source,properties]
----
my.name=MyApp
my.description=${my.name} by ${username:Unknown}
----

YAML 使用 `---` 分隔多个逻辑文档，Properties 使用 `#---` 或 `!---`。
Properties 分隔行不能有前导空白，必须恰好含三个连字符，且其前后行不能使用相同的注释前缀。
后面的活动文档可以覆盖前面的文档。

[source,yaml]
----
my:
  name: MyApp
---
app:
  config:
    activate:
      on-profile: "prod | staging"
my:
  name: DeployedApp
----

`app.config.activate.on-profile` 支持 Profile 表达式；`on-cloud-platform` 可以要求检测到指定云平台，例如 `kubernetes`。
同时指定两个条件时，两者都必须匹配。
YAML 和多文档 Properties 不能直接依靠普通 `@PropertySource` 或 `@TestPropertySource` 加载；这些注解的默认加载方式不等价于应用配置数据加载器。

== YAML

类路径中存在 SnakeYAML 时，配置数据加载器可以读取 YAML。
层次结构会展平成点分隔的属性名，列表会变成 `my.servers[0]`、`my.servers[1]` 等索引属性。
也可以使用 `infra.beans.factory.config.YamlPropertiesFactoryBean`、`YamlMapFactoryBean` 或 `infra.app.env.YamlPropertySourceLoader` 单独加载 YAML。

== 类型安全的配置属性

多个相关属性适合绑定为 `@ConfigurationProperties` 对象，而不是使用大量 `@Value` 字段。
通过 `EnableConfigurationProperties` 显式注册，或使用 `ConfigurationPropertiesScan` 扫描配置属性类。
配置属性扫描与普通组件扫描是不同的机制。

=== JavaBean 绑定

JavaBean 绑定通常使用无参构造器、getter 和 setter。
预先初始化为可变实现的集合、Map，以及预先初始化的嵌套对象，可以省略 setter。
目标还支持公开字段绑定；静态成员不应作为配置属性。
嵌套属性名由成员名决定，而不是由嵌套类型名决定。

=== 构造器绑定

单个有参构造器可以隐式启用构造器绑定；有多个构造器时使用 `infra.context.properties.bind.ConstructorBinding` 明确选择。
record 同样支持构造器绑定。构造器参数名必须保留，编译时使用 `-parameters`。
通过普通组件、`@Bean` 工厂方法或 `@Import` 创建的对象不采用这种配置属性构造器创建方式。

`infra.context.properties.bind.DefaultValue` 为缺失的构造器参数或 record 组件指定默认值，支持占位符解析和类型转换。
嵌套对象未提供属性时通常为 `null`；空的 `@DefaultValue` 可以要求为缺失的嵌套属性创建默认对象。
不推荐把 `Optional` 用作配置属性成员，应根据实际空值语义设计类型。

配置对象中的默认值不会自动写入 `Environment`。
例如一个布尔成员默认是 `false`，不意味着 `@Value("${my.enabled}")` 在未提供属性时一定能解析；仍应显式提供占位符默认值。

=== 使用和第三方对象

配置属性 Bean 可以像其他 Bean 一样注入。
通常应只承载环境配置，不在构造器中注入其他业务 Bean。
也可以在创建第三方对象的 `@Bean` 方法上使用 `@ConfigurationProperties`，为返回的对象绑定指定前缀下的属性。

=== 宽松绑定

绑定时支持连字符、驼峰和下划线等常见命名形式，例如 `first-name`、`firstName`、`first_name`。
注解的前缀必须使用小写连字符形式。推荐配置文件也使用这一形式。
环境变量名转换规则是把点换成下划线、删除连字符并转为大写：`app.main.log-startup-info` 对应 `APP_MAIN_LOGSTARTUPINFO`。
列表索引用下划线包围，例如 `my.service[0].other` 对应 `MY_SERVICE_0_OTHER`。
环境变量绑定到 Map 时，键名会小写化，但值不变。

Map 的特殊键可以用方括号保留，例如 YAML 中的 `"[/key1]"`。
没有方括号时，键中的部分非字母数字字符会被删除。
对于 `Map<String, String>`，点可以保留为键的一部分；对于 `Map<String, Object>`，不加括号的点通常表示嵌套结构。
宽松绑定默认缓存不可变属性源；需要控制缓存时使用 `infra.context.properties.source.ConfigurationPropertyCaching`。

=== 集合合并规则

多个来源中的列表按最高优先级来源整体替换，不追加元素，也不合并同一索引对象的字段。
Map 则可以从多个来源合并不同键，同一属性由更高优先级的值覆盖。
这些规则适用于全部属性源，不限于 Profile 配置文件。

例如，将以下配置绑定到包含 `name` 和 `description` 成员的对象列表：

[source,yaml]
----
my:
  list:
    - name: my name
      description: my description
---
app:
  config:
    activate:
      on-profile: dev
my:
  list:
    - name: my another name
----

未激活 `dev` 时，列表中有一个对象，名称为 `my name`，描述为 `my description`。
激活 `dev` 后，列表仍只有一个对象，名称为 `my another name`；如果对象没有预设描述，描述为 `null`，不会继承低优先级列表同一索引处的描述。
即使低优先级列表有多个元素，也不会保留没有出现在高优先级列表中的元素。

Map 的行为不同。考虑将以下配置绑定到 `Map<String, MyPojo>`：

[source,yaml]
----
my:
  map:
    key1:
      name: my name 1
      description: my description 1
---
app:
  config:
    activate:
      on-profile: dev
my:
  map:
    key1:
      name: dev name 1
    key2:
      name: dev name 2
      description: dev description 2
----

激活 `dev` 后，Map 包含 `key1` 和 `key2`。
`key1.name` 是 `dev name 1`，而 `key1.description` 仍为低优先级来源的 `my description 1`。
`key2` 的两个成员都来自 `dev` 文档。

=== 类型转换

绑定器使用转换服务将文本转换为目标类型。
自定义转换可通过名为 `conversionService` 的转换服务或带 `ConfigurationPropertiesBinding` 的转换器提供。
用于绑定的转换器会较早创建，应限制其依赖；通过 `@Bean` 注册转换器时推荐使用静态工厂方法。

* `Duration` 支持整数（默认毫秒）、ISO-8601 和 `10s` 等形式；`infra.format.annotation.DurationUnit` 可以调整无单位数值的单位。支持 `ns`、`us`、`ms`、`s`、`m`、`h`、`d`。
* `Period` 支持整数（默认天）、ISO-8601 和 `1y3d` 等形式；`infra.format.annotation.PeriodUnit` 可调整默认单位。支持 `y`、`m`、`w`、`d`，周会转换成 7 天。
* `infra.util.DataSize` 支持整数（默认字节）和 `10MB` 等形式；`infra.format.annotation.DataSizeUnit` 可调整默认单位。支持 `B`、`KB`、`MB`、`GB`、`TB`。

迁移已有整数属性为上述类型时，应保留原单位语义，而不是默认假定单位相同。

==== Duration 示例

下面的不可变配置属性类型通过构造器绑定超时值。
使用前需要通过 `@EnableConfigurationProperties` 或配置属性扫描注册类型，并保留编译参数 `-parameters`：

[source,java]
----
import java.time.Duration;
import java.time.temporal.ChronoUnit;

import infra.context.properties.ConfigurationProperties;
import infra.context.properties.bind.DefaultValue;
import infra.format.annotation.DurationUnit;

@ConfigurationProperties("my")
public class MyProperties {

  private final Duration sessionTimeout;

  private final Duration readTimeout;

  public MyProperties(@DurationUnit(ChronoUnit.SECONDS) @DefaultValue("30s") Duration sessionTimeout,
          @DefaultValue("1000ms") Duration readTimeout) {
    this.sessionTimeout = sessionTimeout;
    this.readTimeout = readTimeout;
  }

  public Duration getSessionTimeout() {
    return this.sessionTimeout;
  }

  public Duration getReadTimeout() {
    return this.readTimeout;
  }
}
----

`my.session-timeout=30`、`PT30S` 和 `30s` 都表示 30 秒，因为该参数用 `@DurationUnit` 指定了秒。
`my.read-timeout=500`、`PT0.5S` 和 `500ms` 都表示 500 毫秒，因为未指定注解时默认单位为毫秒。
缺失属性使用 `@DefaultValue`，分别为 30 秒和 1 秒。
JavaBean 绑定也可以在对应字段上使用 `@DurationUnit`，并通过字段初始化提供默认值。

==== DataSize 示例

容量属性同样支持构造器绑定与默认单位：

[source,java]
----
import infra.context.properties.ConfigurationProperties;
import infra.context.properties.bind.DefaultValue;
import infra.format.annotation.DataSizeUnit;
import infra.util.DataSize;
import infra.util.DataUnit;

@ConfigurationProperties("my")
public class MyProperties {

  private final DataSize bufferSize;

  private final DataSize sizeThreshold;

  public MyProperties(@DataSizeUnit(DataUnit.MEGABYTES) @DefaultValue("2MB") DataSize bufferSize,
          @DefaultValue("512B") DataSize sizeThreshold) {
    this.bufferSize = bufferSize;
    this.sizeThreshold = sizeThreshold;
  }

  public DataSize getBufferSize() {
    return this.bufferSize;
  }

  public DataSize getSizeThreshold() {
    return this.sizeThreshold;
  }
}
----

`my.buffer-size=10` 和 `10MB` 等价，而 `my.size-threshold=256` 和 `256B` 等价。
这里的 `KB`、`MB` 等使用二进制倍数，例如 `1KB` 为 1024 字节。
将原先以 MB 为单位的整数属性改为 `DataSize` 时，应保留 `@DataSizeUnit(DataUnit.MEGABYTES)`，避免把既有无单位配置解释为字节。

=== 校验

存在 Jakarta Bean Validation 实现时，可以在配置属性类型上声明 `infra.validation.annotation.Validated`，并为成员添加约束。
嵌套对象的级联校验使用 `jakarta.validation.Valid`。
也可以提供名为 `configurationPropertiesValidator` 的 `infra.validation.Validator` Bean；它的工厂方法应是静态的，避免过早创建配置类。

下面的配置类型要求提供远端地址，并级联校验嵌套的用户名：

[source,java]
----
import java.net.InetAddress;

import jakarta.validation.Valid;
import jakarta.validation.constraints.NotEmpty;
import jakarta.validation.constraints.NotNull;

import infra.context.properties.ConfigurationProperties;
import infra.validation.annotation.Validated;

@ConfigurationProperties("my.service")
@Validated
public class MyProperties {

  @NotNull
  private InetAddress remoteAddress;

  @Valid
  private final Security security = new Security();

  public InetAddress getRemoteAddress() {
    return this.remoteAddress;
  }

  public void setRemoteAddress(InetAddress remoteAddress) {
    this.remoteAddress = remoteAddress;
  }

  public Security getSecurity() {
    return this.security;
  }

  public static class Security {

    @NotEmpty
    private String username;

    public String getUsername() {
      return this.username;
    }

    public void setUsername(String username) {
      this.username = username;
    }
  }
}
----

`Security` 提前初始化为非空对象，因此即使没有提供任何 `my.service.security.*` 配置，也会通过 `@Valid` 检查其 `username` 约束。
仅在嵌套类型上声明约束并不能替代关联成员上的 `@Valid`。
也可以在创建配置属性 Bean 的 `@Bean` 方法上声明 `@Validated` 来触发校验。

=== 与 @Value 的区别

`@ConfigurationProperties` 支持结构化绑定、宽松命名和配置元数据，不求值 SpEL。
`@Value` 适合单个值和需要表达式求值的情况，但不提供等价的配置元数据能力。
应用自定义一组配置键时，推荐把它们归入一个配置属性类。
